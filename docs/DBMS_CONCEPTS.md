# DBMS concepts demonstrated

## Transactions and ACID

`app/services/transactions.py:process_transfer` uses `session.begin()` around the
entire debit, credit, transfer insert, historical SQL, model call, prediction insert,
trigger-generated alert and audit writes. Any exception rolls back the entire unit.

- **Atomicity:** `scripts/demo_rollback.py` intentionally fails inference *after*
  debit/credit and transfer insertion, verifies balances/counts/audits are unchanged,
  and also tests insufficient funds. It does not merely simulate an error in the UI.
- **Consistency:** database checks and ownership FKs plus service validation ensure
  positive amounts, valid account/device owners and conserved same-currency balances.
- **Isolation:** PostgreSQL defaults to READ COMMITTED. The service locks the
  customer's row to serialize history calculations across that customer's accounts,
  then locks both accounts with `FOR UPDATE` in global account-ID order. A waiting
  debit rereads the locked account's committed balance. Device rows are locked before
  changing `last_seen`. SQLite uses `BEGIN IMMEDIATE` before any reads; its isolation
  mechanism is database-wide writer serialization, not row locking.
- **Durability:** committed database rows survive process restart. Docker PostgreSQL
  stores its data in the `banking_postgres` named volume. Do not run `down -v` when
  persistence is required. SQLite stores local rows in `data/banking.db`.

## Concurrency and locking

Run `scripts/demo_concurrency.py`. Disposable source balance is ₹10,000. Two
worker threads pass a barrier then debit ₹8,000 and ₹7,000 on independent
connections. Exactly one succeeds; the other gets insufficient balance. The
remaining balance is ₹2,000 or ₹3,000; source + destination remains ₹10,000 and
exactly one transaction/prediction exists. The result is asserted, not prewritten.

Opposite transfers lock accounts in the same sorted order to avoid account-lock
cycles. Isolation tests against PostgreSQL use disposable schemas so existing
banking rows are never dropped. No optimistic assumption based solely on UI timing
is used. Keep model inference bounded: locks remain held while the model executes.

## Keys, constraints and normalization

See `DATABASE_DESIGN.md` for entities and ER diagram. Database constraints remain
active even for direct SQL inserts; API validation adds clearer errors.
`tests/test_banking.py` tests FK failure, negative balances and mismatched owners.
Financial values are Decimal / NUMERIC rather than binary floats.

## Triggers and audit history

SQL objects are installed by Alembic. `prediction_alert` creates alerts when risk
crosses the shared threshold. Tests include a raw SQL prediction insert to prove
alert creation does not depend on Python service logic.

Update an alert through the dashboard/API and inspect its audit entry. The old and
new status are generated by the database trigger. Trigger writes participate in
the same rollback as their triggering statement. Audit contact fields are redacted
through an explicit allowlist; this is a classroom audit trail, not a tamper-proof
compliance ledger for unrestricted database administrators.

## Indexing and EXPLAIN

The customer/time composite index supports repeated velocity queries without
loading every historical row into Python. `behaviour_features` computes COUNT,
AVG, MAX and conditional time-window sums in SQL, plus one latest-row query.
`index_plan` emits the actual PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` result or
SQLite `EXPLAIN QUERY PLAN`. A small-table sequential scan is an honest result.

## Joins, aggregates, nested queries and views

- Transaction API: INNER JOIN customers, LEFT JOIN predictions.
- Alert API: alerts JOIN transactions JOIN predictions JOIN customers.
- Suspicious view: INNER JOIN predictions and LEFT JOIN alerts.
- Customer summary: LEFT JOIN preserves customers with no transactions.
- Overview: COUNT, SUM and AVG in SQL, distinct alert/classification counts.
- SQL demo: AVG/MAX/MIN/SUM, GROUP BY/HAVING and a correlated historical-average query.

Counts of model-classified FRAUD differ from reviewer-confirmed (RESOLVED) alerts;
a model output does not itself confirm fraud.

## Stored functions

PostgreSQL migration `0002` installs real SQL functions for velocity and customer
statistics. Example: `SELECT * FROM get_customer_transaction_stats('C001');`.
SQLite does not support these stored functions and the UI reports an empty function list.

## Parameterization, validation and error handling

ORM queries and bound SQL parameters handle user input. Table/object identifiers
used for migrations and demonstrations are internal constants, not user SQL.
Customers/accounts/devices must exist and be owned correctly. Invalid amount,
insufficient balance, missing entities, failed inference and database failures
return meaningful HTTP errors without SQL/credentials. Errors leave no partial
banking operation committed. Migrations must precede startup; schema creation is
never hidden inside a request.
